# Implementation Plan: Gate Readiness Programme

**Feature**: [Gate Readiness Programme](spec.md)  
**Branch**: `004-gate-readiness`  
**Status**: Approved for controlled implementation; no gate has passed  
**Data classification**: Internal; synthetic fixtures and safely redacted review evidence only

## Context and requirement coverage

This feature closes the _engineering and evidence-preparation gaps_ identified for G1, ODR-003, ODR-004, and G2. It is not authority to activate a real login, collect real personal data, migrate historic records, create an engagement or matter, clear a conflict, or mark a gate as passed.

**Authoritative dependencies**: LG-SRS-001, LG-GOV-001, LG-GOV-002, LG-GOV-003, LG-SEC-001, LG-PRV-001, LG-LEG-VAL-001, LG-PRD-002, LG-DOM-001, LG-QA-001, LG-DEV-002, ADR-005, ADR-006, ADR-009, and ADR-010.

No web route, client projection, provider SDK, or public API is in scope.

**Explicit exclusions**:

- Selecting, activating, or contracting an identity, cloud, storage, monitoring, or MFA provider (ODR-005).
- Processing real employee, prospect, client, party, matter, document, or identity data.
- A public intake form, public login, staff login, account recovery screen, client portal, or browser session.
- A conflict-clearing, engagement, matter-opening, representation-authority, break-glass, migration, retention/destruction, or legal-decision workflow.
- Any representation that G1, ODR-003, ODR-004, or G2 is closed before its named accountable owner records approval.

## Bounded design

### G1: append-only access lifecycle

1. Keep the existing M1 membership and grant rows immutable as legacy evidence. Deprecate new writes to them after the lifecycle migration; do not update, delete, or reinterpret a historical row.
2. Introduce explicit domain commands: `GrantMembership`, `GrantRestrictedResourceAccess`, `SuspendAccess`, `ReinstateAccess`, `RevokeAccess`, `CorrectAccessRelationship`, and `OffboardAccount`. No generic status update is permitted.
3. Each command carries an opaque command ID, correlation ID, trusted operator, organization, subject, exact scope, expected revision, effective/expiry time where applicable, reason code, and required approval reference. An approval reference resolves to one immutable, organization-scoped approval record containing requester, distinct approver, subject, exact scope, approval time, and expiry. It must fail closed on malformed input, cross-organization scope, unauthorized administration, self-expansion, stale revision, expired relationship, expired approval, or incompatible replay.
4. A new or expanded relationship records separate requester and approver identities; they must be distinct and independently authorized to administer the organization. A safety-preserving suspension, revocation, or offboarding records the responsible operator and may take effect immediately. Break-glass remains unavailable and denied.
5. Membership and grant lifecycle event ledgers are immutable. A correction, suspension, reinstatement, revocation, expiry, or offboarding appends a successor event instead of changing its predecessor.
6. Rebuildable effective-membership and effective-grant projections carry the aggregate identity, organization/scope, state, revision, effective/expiry times, and last event reference. They are derived data, not an audit substitute. The authorization adapter reads only these projections.
7. An immutable command receipt fingerprints the complete command request. Exact replay returns the original outcome; reuse of a command ID with different content fails without creating state. Lifecycle state, receipt, audit evidence, and a privacy-safe outbox intent commit atomically.
8. The authorization decision evidence records the effective membership/grant revision used to make the decision. A suspended, revoked, expired, offboarded, wrong-organization, role-only, browser-asserted, malformed, or unapproved-emergency request produces the existing generic denial.
9. The provider-neutral identity port may expose verified-principal reference, session expiry, authentication-strength reference, and invalidation intent. It must not import a provider SDK or accept a browser claim as proof. A future approved provider consumes the invalidation intent; server-side access checks remain mandatory on every protected operation.

### ODR-003: privacy/DPO review packet and safe guardrails

1. Create a versioned Processing Review record for each future real-data workflow. It has accountable legal entity, controller/processor role, purpose, proposed lawful basis, data/subject categories, sensitivity, collection source/channel, access boundary, recipients/processors, hosting/transfer position, retention/legal-hold treatment, rights and breach routes, security controls, owner, and reviewer outcome.
2. Treat the privacy notice, consent request, and consent evidence as three distinct artifacts. Consent is used only if the privacy/DPO reviewer selects it as an appropriate lawful basis. A future consent flow must require affirmative, specific, accessible choice and withdrawal; no preselection, implication, or bundled consent is allowed.
3. Include a DPO determination packet: legal-entity/data-user assessment, nominated reviewer, registration/category/appointment evidence, independence/conflict assessment, contact and reporting route, resourcing, and replacement plan. Its outcome is a reviewer/legal conclusion, not an engineering declaration.
4. Keep high-risk intake material blocked by default: national/passport identifiers, children’s data, health information, biometrics, case facts/evidence, criminal/allegation information, and any uncertain sensitive category. Before approval, the only permitted pattern is synthetic fixtures and a future minimal contact-and-callback design with no confidential-content capture.
5. Maintain a provider/processor/transfer review template connected to ODR-005. Missing vendor, hosting region, support access, contract, retention/deletion, security evidence, or transfer approval blocks the provider.
6. Define future rights, retention/legal-hold, and breach records as separate controlled workflows. No automated destruction, generic "erase everything", hard-coded legal deadline, or transfer is introduced by this feature.

### ODR-004: pilot operating profile and no-migration baseline

1. Create a controlled Pilot Operating Profile (POP) template for Product and legal operations. It records objective, legal entity/offices, selected practice areas and exclusions, bilingual terminology, provisional taxonomy, roles/handoffs/escalations, approved/disabled channels, accessibility needs, volumes, current systems/physical records, source quality, authoritative-system map, lifecycle playback, assumptions, risks, evidence, change triggers, and sign-offs.
2. Discover only through structured interviews, observed walkthroughs, safely redacted artifacts, role/playback sessions, and usability assessment. Each finding records participant role, source reference, confidence, date, classification (fact/need/proposed design/rejected assumption/risk/open decision), and requirement IDs. Client content never enters the repository.
3. Record the approved default: the first pilot is greenfield. No historic client, prospect, party/contact, matter, document/evidence, financial, user, or access records are imported or manually re-keyed to bypass the gate.
4. A future migration needs a separately signed Migration Decision Pack: lawful authority/source inventory; ownership and authoritative-source matrix; field map/exclusions; privacy, legal-hold, security, and conflict implications; quality thresholds; synthetic/redacted dry run; reconciliation/error queue; provenance; reversible rollout; and Product, Privacy/DPO, Security, and lawyer approvals as applicable.

### G2: lawyer scenario packet and M3 boundary

1. Create a versioned, synthetic-only Egyptian-lawyer scenario pack. Every case identifies fictional facts/unknowns, Arabic/English/Latin name forms/provenance, linked parties, candidate cues, authorized role, requested decision/question, source location, safe system behaviour, prohibited automated behaviour, escalation, and the reviewer outcome (`approved`, `conditional`, `rejected`, or `deferred`) with scope, compensating behaviour, owner, expiry, and release impact.
2. Include at least these nine scenario families: incomplete enquiry; Arabic/English/transliterated/former name variation; similar but distinct person/organization or affiliate; disputed/expired/withdrawn representative claim; current client/proposed adverse party; former client with incomplete scope/timing; prospective adverse party; enquiry/consultation/payment without engagement; and restricted or uncertain high-sensitivity case.
3. M3 remains a separate feature. It must translate lawyer-approved outcomes into explicit commands such as recording an enquiry/candidate, requesting information, submitting for review, recording an authorized disposition, activating engagement, and opening a matter. It must prove that no candidate cue or absence of a string match can auto-clear a conflict, establish engagement, create authority, create matter access, or merge parties.
4. ODR-004 may be closed only by Product/legal-operations approval of a completed POP. G2 remains blocked until the M3 workflow and its evidence exist and a lead practising Egyptian lawyer signs the scenario outcomes.

## Delivery and verification

1. **Evidence and boundary setup** — add `verification.md`, review-packet templates, scenario fixtures, prohibited-scope regression coverage, and M1/M2 traceability links. Keep ODRs/gates open.
2. **G1 domain/application contract** — write failing tests first; introduce typed lifecycle states, commands, error semantics, requester/approver distinction, command receipts, and provider-neutral session invalidation intent.
3. **G1 persistence and migration** — add ledgers/projections/immutable guards, backfill legacy synthetic relationships, transactional audit/outbox, serialization, and projection reader. Update M1/M2 test fixtures away from direct legacy writes.
4. **G1 verification and reviewer package** — run migration, concurrency, negative authorization, privacy-safe logging, recovery, and full repository checks; produce a Security/Engineering review packet. G1 stays blocked until external evidence is supplied.
5. **ODR-003 / ODR-004 / G2 packets** — complete privacy/DPO, POP/no-migration, migration-decision, and lawyer-scenario templates. Record only actual reviewer outcomes, never placeholders as approvals.
6. **Convergence and handoff** — update the requirement traceability and both M1/this feature verification records; run `pnpm verify` and `pnpm verify:full`; perform the convergence. Report blockers plainly.

**Rollout and recovery**: The lifecycle code ships disabled from real identities and data. An additive migration preserves legacy M1 records, creates effective projections, and keeps revoked access denied under code rollback. No destructive down migration or legacy-data import is authorized. A future activation requires configuration controlled by the G1/ODR-003/ODR-005/G2 approvals and a tested rollback/incident plan.

**Independent review required**: Security and Engineering leads for G1; Privacy/DPO reviewer (with Egyptian legal support) for ODR-003; Product and legal-operations leads for ODR-004; lead practising Egyptian lawyer for G2. The Project Sponsor's approval authorizes this work but does not replace any of these reviews.

**Completion commands**: `pnpm db:generate`, clean disposable `pnpm db:migrate`, focused domain/application/database/testing commands, `pnpm verify`, and `pnpm verify:full`. The final [verification record](verification.md) must retain requirement coverage, exact command/date/result, migration/recovery evidence, reviewer outcomes, residual risk, and blocked activation conditions.
