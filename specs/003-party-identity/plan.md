# Implementation Plan: M2 Party Identity Foundation

## Context and requirement coverage

This plan implements the approved, reversible foundation for **DAT-PRT-001**. Its controlling records are `LG-SRS-001`, the structured requirement and traceability records, `LG-DOM-001`, ADR-001/002/005/006/009/010, `LG-API-001`, `LG-PRV-001`, `LG-DEV-002`, and the M2 [feature specification](spec.md). The release gate is **G2 Legal intake and conflicts**. The feature has P1 product risk and privacy/legal workflow sensitivity; all implementation and tests use local, synthetic data only.

The product approval recorded on 2026-08-10 authorizes implementation of the bounded, internal foundation. It does not pass G2 or authorize real personal-data processing, legal identity verification, representation decisions, conflict clearance, engagement, matter opening, or a public/client-facing intake surface. ODR-003, ODR-004, and G2 legal scenario validation remain activation blockers in [verification.md](verification.md).

Current implementation review: M0 provides PostgreSQL, an audit/outbox foundation, and provider-neutral package boundaries. M1 provides a provider-neutral trusted `Actor`, explicit server-side authorization evaluation, organization membership and exact-resource grants, and PostgreSQL integration-test conventions. M1 G1 activation and relationship-revocation design remain open, so M2 reuses only its synthetic exact-grant evaluation and does not claim production access-lifecycle readiness. The repository has no party, contact, client, engagement, matter, enquiry, conflict, representation, identity-provider, or public intake route. `packages/domain` is framework-independent; `packages/application` owns ports and explicit commands; `packages/database` owns Drizzle/PostgreSQL adapters and migrations.

Affected areas: `packages/domain`, `packages/application`, `packages/database`, `packages/testing`, structured requirement traceability, and `specs/003-party-identity`. No `apps/web` or public/API route is in scope. The existing M1 authorization foundation is reused; no new identity provider, session, role, provider, cloud service, or migration source is selected.

Explicit exclusions: real client/prospect/contact/identity data; national IDs and identity documents; import or source migration; public intake; client portal; conflict search or clearance; client/engagement/matter/proceeding state; legal authority verification; merge or deduplication automation; generic status PATCH routes; legal conclusions; provider activation; and G2 activation.

## Bounded design

### Domain, commands, and queries

`packages/domain` will define pure party-identity value types, accepted vocabulary, validation errors, and command validation. It has no dependency on Next.js, Drizzle, Node runtime, providers, or database types. A neutral `Party` has exactly one kind (`person` or `organization`) and does not encode prospect, client, engagement, matter, proceeding, authorization, or legal verification state.

`packages/application` will expose explicit, server-only commands. Each command receives a trusted M1 `Actor`, a correlation ID, an immutable command ID, an authorization port, and a party-identity persistence port. There is no generic update/status command.

| Command                     | Authorized resource and operation                     | Result and prohibited behavior                                                                                                                                           |
| --------------------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `createNeutralParty`        | `party-registry` / actor organization, `party.create` | Creates a person or organization and its first name assertion. It cannot create a client, engagement, matter, or authority.                                              |
| `recordPartyName`           | `party` / party ID, `party.record_name`               | Adds an alias or a correction lineage; never overwrites a prior name.                                                                                                    |
| `recordPartyContact`        | `party` / party ID, `party.record_contact`            | Adds a purpose-limited contact assertion; it never proves identity, consent, authority, or client status.                                                                |
| `recordRepresentationClaim` | Both `party` IDs / `party.record_representation`      | Records a sourced claim between two parties; it never grants access or establishes legal representation.                                                                 |
| `flagPossibleDuplicate`     | Both `party` IDs / `party.flag_possible_duplicate`    | Records a candidate pair only; it never merges, selects a canonical party, or clears a conflict.                                                                         |
| `readPartyIdentityHistory`  | `party` / party ID, `party.read`                      | Produces an internal server-side projection of assertions and history. It never returns a client-portal projection or exposes party existence to an unauthorized caller. |

The application calls M1 `evaluateRestrictedResourceAccess` before each party read or mutation. Creation uses the organization-scoped registry resource; ordinary operations use the exact party resource; representation and duplicate commands authorize both linked party IDs before either record is read or written. A denial yields the existing generic `not_authorized` outcome and stops the operation before any party read/write. A party-history read returns only the target party’s own data; a future linked-party read requires its own exact-party authorization. The M1 decision evidence remains separate from party identity facts. A future authority-provisioning workflow is explicitly out of scope.

### Identity assertion model and historical integrity

The authoritative data design is detailed in [data-model.md](data-model.md). In summary:

- Parties are organization-scoped neutral records with opaque UUIDs and an immutable `person` or `organization` kind.
- Every identity assertion records purpose, classification, subject category, source, retention candidate, access boundary, and validation requirement. M2 fixes those values to a synthetic-development posture; none is a production privacy approval.
- Name forms retain value, language tag, optional script, form type, review state, recording time, metadata, and optional predecessor. A separate append-only primary-name assignment chain identifies the current primary without rewriting a name. This preserves former/transliterated/alternate names and their provenance.
- Contacts retain only a synthetic contact value, type, operational purpose, review state, recording time, and metadata. The design deliberately has no consent, verified-identity, client, or legal-authority column.
- Representation claims retain represented/representative party IDs, a non-authoritative claim state (`asserted`, `disputed`, `withdrawn`, or `expired`), review state, effective dates where supplied, metadata, and correction lineage. These values are workflow facts, not Egyptian-law conclusions.
- Possible-duplicate flags retain an ordered pair of distinct parties plus review state and metadata. They are review cues only and have no merge/clearance command or event.

All M2 tables carry the organization scope. PostgreSQL composite foreign keys on `(organization_id, party_id)`, `NOT NULL` fields, unique lineage constraints, a distinct-pair constraint, and pure domain validation prevent cross-organization or malformed assertions. Append-only triggers reject `UPDATE` and `DELETE` on each M2 party/identity/audit-receipt table. Corrections require a new explicit command and a predecessor reference. `reviewed` means only that a recorded assertion received the named workflow review; it never means legally verified, authorized, or conflict-cleared.

### Persistence, audit, events, concurrency, and recovery

`packages/database` will add a Drizzle schema and additive generated migration for the M2 tables. A reviewed custom SQL migration will add the append-only triggers, following the M1 migration pattern. The database adapter implements the application port and performs each successful party mutation in one PostgreSQL transaction with:

1. the new immutable party/assertion rows;
2. a new append-only, organization-scoped party-identity audit/command-receipt record with actor, action, opaque resource ID, command ID, correlation ID, and timestamp; and
3. a minimal `outbox_events` record whose payload contains only opaque IDs, event type, and non-sensitive assertion category.

No actual name, contact value, source text, or representation claim is placed in logs or outbox payloads. Outbox delivery remains inactive under the M0 provider boundary. Structured logs contain only correlation ID, command name, generic authorization outcome, and opaque IDs when necessary for technical diagnosis.

Database mutations use a serializable transaction where a correction or primary-name lineage is read and extended, then rely on primary/unique constraints to reject conflicting duplicate command IDs or lineage forks. The organization-scoped party audit/command receipt is the replay record: a retried mutation must exactly match its existing semantic input before returning its existing result; a command ID with different semantics is rejected. Every other failure closes without a partial party row, receipt, or outbox event. There is no HTTP retry contract because no HTTP/API surface is introduced.

An unsuccessful authorization, validation, organization-scope, FK, uniqueness, or event write rolls back the entire party mutation. A nonexistent or cross-organization party is surfaced to a caller only as a generic authorization/not-found boundary error; no query may enumerate party existence. The database retains append-only historical data on application rollback. Rollback is code rollback plus the approved database-change process; no destructive down migration or data deletion is permitted.

### Interface, UI, locale, and operating posture

The only contract is the internal, typed application contract in [contracts/party-identity.md](contracts/party-identity.md). No HTTP route, server action, page, client component, browser form, provider callback, or portal projection is created. Therefore English/Arabic/RTL, keyboard, screen-reader, and automated WCAG checks are not applicable to this M2 implementation; their future acceptance evidence is retained as a requirement for a later intake UI.

The foundation is dark by default: no runtime composition calls these ports until a separately approved internal surface is designed. This is an implementation-control posture, not a feature flag or an activation claim.

## Delivery and verification

1. Add pure domain types/validation and test the positive and prohibited identity cases first.
2. Define application ports and explicit commands, then test authorization-negative and non-persistence behavior with fakes.
3. Add the additive Drizzle schema, generate/inspect the migration, add the custom append-only trigger migration, and build the transactional PostgreSQL adapter.
4. Run clean synthetic migration and integration tests for provenance, scope isolation, event atomicity, idempotency, and immutability.
5. Update structured traceability paths/evidence and [verification.md](verification.md), including every command result, migration evidence, residual risk, and remaining G2 blocks.
6. Run `pnpm verify` and `pnpm verify:full` with synthetic local PostgreSQL, then run the convergence review. Any taskable convergence finding is appended to `tasks.md`, implemented, and re-checked before technical handoff.

The schema change is additive and unactivated. There is no production rollout, feature flag, import, backfill, or external side effect. Technical completion means the synthetic foundation is implemented and verified; it does not mean G2 is passed or any personal-data/intake/legal capability is activated.
